# Before You Commit — classroom readiness implementation prompt

Act as a senior TypeScript engineer, AWS serverless developer, database change reviewer, and DBMS teaching assistant. You are working on the existing Before You Commit repository. Deliver the smallest reliable classroom release, in the order below. Start by reading the current source and tests, checking the working tree, and recording the baseline. Preserve existing user changes and keep changes reviewable.

## Product goal

A student opens a fictional change ticket and previews a SQLite UPDATE against starter data. A reviewer adds a plausible booking that reveals a broader update. The student adjusts the predicate and sees the intended change alongside evidence that the added booking was preserved. A replay link lets a classmate reproduce that exact review.

Aarav is the reference exercise. Registration #204, his 10:00 AM Amazon interview, should move from scheduled to cancelled. The initial query passes on starter records. With #188, his 2:00 PM Facebook interview, added, the same query changes both registrations. The corrected query changes only #204 and leaves #188 scheduled. The starter pass and the pass with reviewer records represent different claims. Carry that distinction through the interface, reports, and project documentation.

Keep browser-local SQLite and the Web Worker, the static scenario bank, and the AWS replay API. The AWS path serves the app and persists replay recipes. Bedrock is optional instructor tooling for authoring fictional scenario details. Students can preview and grade challenges without a model call. Keep the shipped app focused on the exercise.

## Release blockers — correctness and reproducibility

1. **SQL validation and grading.** Review src/engine/sqlValidator.ts, sqlEngine.ts, diffEngine.ts, and workerClient.ts together. The audit found that a non-status field could change while the grader returned a pass. It also found that preprocessing changed the contents of a quoted SQL value. Define the supported SQLite UPDATE form explicitly and enforce the permitted statement, table, and assignment column through a SQLite-aware parser or a small, rigorously defined grammar. Keep quoted values intact. Use a second check on the actual SQLite result to compare all persisted fields, detect changed row identities or unexpected rows, and require exact expected final state. Treat affected rows and actual value changes distinctly in the interface. Keep valid legacy exercise SQL accepted. Review the worker timeout and cancellation behavior under deterministic failure and keep the editor responsive when the worker cannot start. Add contract tests for the accepted SQL grammar and quoted-text preservation. Use synthetic before-and-after snapshots to test forbidden field changes and unexpected row identities independently of SQL parsing.

2. **Replay validation.** Review src/api/replayApi.ts, src/scenarios/index.ts, src/App.tsx, backend/src/handler.ts, and the engine entry point. A malformed recipe currently can replace an existing seed registration. Reject unsafe-integer IDs, duplicates, collisions with seed IDs, malformed row fields, unsupported provenance values, excessive row counts, and oversized payloads. Apply compatible validation to cloud writes, cloud reads, self-contained links, and the worker boundary. Use one schema or demonstrate parity across boundaries. Validate bytes where the contract specifies bytes. A new replay must identify the exact scenario ID, scenario version, and exercise. Reserve defaulting for deliberately documented historical formats. Explicit unknown exercises and missing required version fields should yield understandable errors. Preserve known Cloud Quest legacy links and historical Aarav versions. Use a versioned recipe contract if needed. Never silently overwrite seed data or show a different exercise as a successful restore.

3. **Instructor approval.** Review scripts/authorChallenge.mjs and the scenario registry. The audit found that an explicit missing draft fell back to another draft, and a failed integrity check could leave a file changed. Require an explicit reviewed draft identifier or path and a digest to approve. Validate the identifier, exercise, version, draft data, and output location before writing. Validate model output against a bounded schema. Safely encode generated labels where they are used in SQL literals. Run the same grading rules as the student app, or establish parity through exact before/after fixtures. Verify the exact changed IDs and all preserved fields for seed, failing reviewer, and corrected reviewer runs. Publish by immutable scenario ID and version, preserving historical lookup. Reject conflicting republish attempts and make identical retries safe. Stage and validate the generated scenario and registry together so a failed approval leaves both intact. Approval must work offline. Report local registration and public deployment as separate states.

## Student and reviewer workflow

4. **Guide the student through the experiment.** Use the ticket, candidate SQL, starting records, Preview change, result, and reviewer action as one coherent flow. Explain the meaning of a starter pass in one sentence. Respect the distinction between testing a query and proving it correct for future data. Add progressive help. Start with a conceptual hint about which rows the predicate matches, then reveal the worked answer when requested. Avoid revealing supplied reviewer details through first-load copy or tooltips before the student chooses a hint or example. Keep the ticket specific enough to identify the intended record. Fix unsupported “Room 3” wording in a new active Placement Drive version and preserve historical versions.

5. **Make the evidence easy to interpret.** Keep the side-by-side workspace on desktop and the existing mobile card flow. Show the intended and unintended bookings with date, time, person, and before/after value. Keep preserved reviewer records visible. Keep the complete dataset accessible. Clearly mark stale results while the SQL or data changes. Consider one lightweight “Which rows do you expect this WHERE clause to match?” prompt or an explicit reveal of matching rows after preview. Use evidence from three uncoached classmates to decide whether it earns its place. Make “Create my own booking” the natural path and “Use supplied example” an explicit alternative. Help students choose a fictional student and enter a valid booking without giving away the full counterexample. Keep route provenance in replays.

6. **Make editing and sharing predictable.** Audit reset labels, focus after actions, draft loss on challenge switches, and working with two tabs. Consolidate duplicate reset actions where they do the same thing and distinguish resetting SQL from starting the exercise over. Treat Developer and Reviewer as activity labels and simplify them if they duplicate the workflow. Keep keyboard and screen-reader access. Make it clear whether a link contains current SQL or the last reviewed run. Mark an unpreviewed draft clearly if it can be shared. Add request timeouts and retry/fallback states. Explain what is shared, who can open it, and when a cloud replay expires. Preserve legacy link decoding. Evaluate using a URL fragment for newly generated self-contained links and a copy/export option for recipes too large for a practical URL. Clearly distinguish cloud outages from rejected input.

## AWS release and maintenance

7. **Make builds reproducible.** Review package.json, backend/package.json, the lockfiles, scripts/copy-wasm.js, template.yaml, the deploy workflow, and README.md. A frontend production build passed with a browser bundling warning about node:path. The standalone backend build stopped because esbuild was missing and the backend directory had no lockfile. Establish a repeatable clean install and build for both projects, including a tested Lambda package with its actual SDK dependency strategy. Align the build target and Lambda runtime. Check the current official AWS runtime matrix and region support, then move from deprecated Node.js 20 to a supported runtime. Keep only the WASM assets the build and supported tests require. Confirm a clean build serves the expected WASM with the proper MIME type.

8. **Keep cloud sharing predictable and observable.** Verify the private S3 origin and CloudFront access control, scoped DynamoDB permissions, replay expiration on read, and frontend/API configuration. Add structured logs with request correlation and bounded retention, and alerts for actionable error and throttle signals. Keep raw SQL and booking data out of routine logs. Return useful public error codes, with internal exception details kept in logs. Treat cross-origin configuration, API throttling, and an abuse or spend plan as separate controls. Choose a proportionate policy for an anonymously accessible classroom share endpoint. Verify what the frontend CDN forwards and caches, especially replay query strings and self-contained link content. Use cache settings suitable for hashed assets and the HTML entry point. Document how to deploy and roll back the frontend and backend independently. Avoid replacing the DynamoDB table or deleting existing replays as part of the release.

## Keep the project small

Defer student accounts, live collaboration, a grader dashboard, arbitrary schemas, a public Bedrock endpoint, extra exercises without a new teaching objective, and analytics that store student identity. Remove inaccurate claims such as “strict AST guard” while the implementation uses regex checks, and “zero server state” when cloud replays use DynamoDB. Replace duplicated instructions, decorative status badges, obsolete assets, and generated build artifacts only after checking their references. Use synthetic values throughout demonstrations and tests.

- Return a concise change report, known limitations, a release checklist, and links to evidence. If deployment has already been authorized and the target account is available, verify changes in staging and follow the established delivery workflow, then smoke test CloudFront and the replay API. Keep deployed, locally verified, and unverified claims distinct.
